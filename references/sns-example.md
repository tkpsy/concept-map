# 分身SNS：中間ノードの導出とファイル例

実例から名称・パス・課題番号を一般化した、架空のSNSの例。
動作・実装状態・論点は説明のための設定であり、実際のプロジェクトにはその資料から読み取れる概念を使う。

## 「AI自動行動」ができるまで

まず、具体的な概念を動作まで説明する。

- 自動投稿：アカウントが自分で投稿を作り、時間をずらして出す。
- 自動返信：公開済みの投稿を拾い、返信する。
- 自動反応：アカウントが自律でいいねやフォローをする。未実装。

この三つは、「人が操作していない間、このアプリでは何が起こる？」という問いに答えている。
まとめた説明は「アカウントが、人の操作なしにSNS上で活動する」。
この説明に **AI自動行動** という名前を付ける。抽象的な名前でも、何をまとめたものかを説明できる。

```text
分身SNS
└── AI自動行動
    ├── 自動投稿
    ├── 自動返信
    └── 自動反応
```

ここで確認するのは、「自動返信について知りたい人が AI自動行動を開きそうか」。
名前だけで子を探せ、親の説明から三つの子が並ぶ理由も分かる。

### ファイルにすると

この枝だけに範囲を絞った、五つのファイルで閉じる例。すべて `docs/map/` の直下に置く。

#### 分身SNS.md

```markdown
# 分身SNS

人とAIが同じタイムラインで活動するSNS。アカウントは自律で活動し、
ユーザー自身も並行して投稿できる。このマップでは自律動作を説明する。

- [[AI自動行動]]
```

#### AI自動行動.md

```markdown
# AI自動行動

アカウントが、人の操作なしにSNS上で活動する。ユーザー自身の手動投稿も並行できる。
自動投稿と自動返信は動いており、自動反応は未実装。

判断は worker 側にあり、tick が定期的に回している。

- [[自動投稿]] [[自動返信]] [[自動反応]]
```

#### 自動投稿.md

```markdown
# 自動投稿

アカウントが自分で投稿を作り、時間をずらして出す。
tick が在庫の切れたアカウントを見つけて補充する。

生成エンジン が作り、公開制御 が出す時刻を決める。

## 経緯

素材のある topic でしか生成しない。素材なしでは中身のない文章になりやすいため、
書けないことを許容している。
```

#### 自動返信.md

```markdown
# 自動返信

公開済みの投稿を拾って返信する。入力は、親投稿・自分の過去投稿・返し方。
自動投稿 と違い、素材 は参照しない。

services/replies.py
```

#### 自動反応.md

```markdown
# 自動反応

未実装。アカウントが自律でいいねを打ち、フォローを返す役割を予定している。

## 論点

フォローへの応答は、常に返すか、関心が近い相手だけに返すか。
判断には、交流の増え方と意図しないフォローの頻度を比較する必要がある。

example/social-app#22
```

未実装の概念もファイルは存在するので、予定が見え、リンク切れにもならない。
worker・tick・生成エンジン・公開制御は動作を説明するための言及で、この枝では素の名前を書く。
全体のマップでは、それぞれを読者が探しやすい枝に置く。

## 同じ手順で「後処理」を作る

別の具体的な概念から始める。

- 埋め込み：投稿を意味で検索するためのベクトルを作る。
- 分類：投稿に topic を付ける。

この例では、手動投稿にはこれらの情報がまだなく、投稿後にまとめて補っている。
このまとまりは「投稿後に、検索などに必要な情報を補う」と説明できる。名前は **後処理**。

```text
worker
└── 後処理
    ├── 埋め込み
    └── 分類
```

AI自動行動 は共通する体験、後処理 は共通する仕事から作ったまとまり。
親を一律の分類軸で決める必要はなく、その場所で説明が通る観点を選べる。

## 親の候補が複数あるとき

自動投稿は、AI自動行動とも生成エンジンとも関係する。
このマップでは、自動投稿の仕様は「何が自動で起こるか」を探す入口である AI自動行動 に置く。
文章をどう作るかという詳細は 生成エンジン で説明し、自動投稿の本文から名前で言及する。

既存の木を育てるときは、読者が使っている入口も判断材料になる。
別の親を選んでも説明が通る場合はある。唯一の分類を当てることより、選んだ道順で仕様を探せることを確かめる。
